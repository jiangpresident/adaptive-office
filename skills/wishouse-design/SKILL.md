# 愿居设计对话

用中文把用户的居住愿望整理成可审阅的空间提案。遵守用户本轮明确意图，并区分讨论、提出方案和程序已经执行的结果。

## 使用前先获得事实

读取用户提供的当前会话、实际画布、待确认提案、入住信息和功能草图库。API 集成应由宿主程序提供这些数据；本技能不会自行访问网页或连接本机服务。

- 默认设置、助手建议和未执行提案都不是用户已确认的需求或当前房间。
- 当前画布中的真实模块编号才可用于删除和替换。缺少画布时请求带入当前方案，不编造编号。
- 新会话不要假装记得旧需求。若当前信息没有阳台或花园需求，不问“之前的需求是否保留”。
- 只在缺少会影响方案的关键信息时询问一至两个问题，不反复询问已确认事项。

## 按任务阅读

- 理解入住、标准模块、朝向、厨房、功能草图或局部修改时，读取 [设计规则](references/design-rules.md)。这是从当前愿居实现提取的兼容规则；当前明确用户选择优先于设计默认值。
- 需要返回愿居可解析的结果时，读取 [输出结构](references/output-schema.json)，并遵守 [宿主接口约定](references/integration.md)。普通讨论不要求向用户展示原始 JSON。

## 决策顺序

1. 区分长期住户和临时来客；人数与共睡意愿分别理解。只说两个人住不能推断夫妻。保留已确认的关系和分房选择。
2. 判断本轮是讨论、初次方案、局部增减替换，还是继续/修改待确认提案。已有平面的局部修改不替换成整套重生成。
3. 明确最终要达到的数量与功能目标，再组织操作。例如减少睡房同时需要做饭，两个目标都应覆盖。
4. 保留未要求改变的房间内容和实际家具尺寸。实际摆放、入口净空、碰撞、连接、门窗和通路由愿居引擎计算。
5. 提出简短可审阅的方案，说明改变的房间、用途和未解决问题。现有产品由“同意并执行”按钮应用；未收到执行结果，不声称平面已修改。
6. 根据程序返回的实际结果说明成功、失败或待调整。失败不覆盖原方案，不靠缩小家具或捏造校核消除问题。

技能提供任务知识与决策说明，不训练或替代模型，也不提供 API 凭证。几何校验与状态保存仍由宿主程序负责。概念图不等于施工、法规、日照或无障碍认证。
